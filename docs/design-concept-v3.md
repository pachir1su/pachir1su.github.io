## 0. 결정 사항

이슈 #114 댓글에는 서로 배타적인 두 방향이 있었다.

1. 우주 / 별자리로 컨셉 변경
2. 혹은 #112 · #113을 참고해 **노트 스타일을 유지하고 UIUX만** 변경

저장소 소유자 결정으로 **둘을 버전으로 나눈다.**

| 버전 | 범위 |
|---|---|
| **v2.1.0** (이번 작업) | 노트 컨셉 유지. 정보 전달력 · UIUX · 런타임 성능만 개선 |
| **v3.X.X** (이후) | 디자인 컨셉 자체 변경. 이 문서가 그 준비 문서다 |

> … 컨셉 · 디자인은 손댈 필요가 없다.

즉 30초 테스트를 막고 있던 것은 컨셉이 아니라 정보 위계 · 증거 부재였다.

## 3. 컨셉 후보

이슈 #114의 우주 / 별자리를 포함해 6개를 놓고 비교한다.
모두 이 저장소의 실제 콘텐츠(프로젝트 31개 · 수상 4개 · 실패 5개 · 이중 언어)를
담을 수 있는지를 기준으로 본다.

### A. 우주 · 별자리 (이슈 #114 원안)

- **축**: 프로젝트를 별로, 분야 연결을 별자리로. 연도는 궤도 · 성단.
- **강점**: 프로젝트 간 관계를 그림으로 말할 수 있다. `mindmap.html`이 이미 있어
  개념이 겹치고, 다크 모드가 기본값이 되어 자연스럽다.
- **약점**: 어두운 배경 + 작은 발광 텍스트는 본문 가독성과 대비를 잃기 쉽다.
  실패 섹션 · 진행 상태 같은 **부정 정보**를 별자리 은유로 표현하기 어렵다.
- **비용**: 높음. 배경 렌더링(캔버스 or SVG)이 새로 필요하고 성능 감사가 지적한
  `상시 rAF` 문제를 다시 만들 위험이 크다.
- **리스크**: 장식이 정보를 덮는 실패로 되돌아갈 수 있다(PR #112의 핵심 지적).

### B. 청사진 · 설계도 (Blueprint)

- **축**: 시안 청색 배경 + 흰 선, 치수선 · 부품 번호 · 도면 프레임.
- **강점**: 하드웨어 · 임베디드 프로젝트 비중이 높은 이 포트폴리오와 직접 맞는다.
  `문제 / 한 일 / 결과` 3단 계약을 도면 주기(annotation)로 표현할 수 있다.
- **약점**: 단색 계열이라 수상 카드의 금 · 은 · 동 구분이 약해진다.
- **비용**: 중간. 현재의 선 · 격자 자산을 상당 부분 재사용할 수 있다.

### C. 터미널 · CLI

- **축**: monospace 전면, 프롬프트 · 출력 블록 구조, 필터를 명령어로.
- **강점**: 개발자 독자에게 신호가 가장 직접적이다. 이미 `--font-mono`가 있다.
- **약점**: 한글 monospace 조판이 길어지면 읽기 어렵다. 이중 언어와 상성이 나쁘다.
  개발자가 아닌 독자(교수 · 대회 심사)에게 진입 장벽이 생긴다.
- **비용**: 중간.

### D. 실험 노트 · 아카이브 (현재 컨셉의 확장)

- **축**: 노트를 버리지 않고 **연구 노트 / 로그북**으로 좁힌다. 날짜 · 기간 ·
  관측 · 결과 칸이 컨셉 자체에 들어 있다.
- **강점**: PR #112가 지적한 **기간 · 결과 · 배운 점 부재**를 컨셉이 강제한다.
  기존 CSS 자산 재사용률이 가장 높고 회귀 위험이 가장 낮다.
- **약점**: "컨셉을 바꿨다"는 인상은 가장 약하다.
- **비용**: 낮음.

### E. 인쇄 편집 · 신문 조판 (Editorial)

- **축**: 그리드 · 큰 표제 · 컬럼. 장식 대신 타이포그래피로 위계를 만든다.
- **강점**: 정보 밀도가 높은 이 사이트(카드 31개)와 잘 맞는다. 장식 인터랙션
  9종을 자연스럽게 정리할 명분이 된다.
- **약점**: 개성이 약해질 수 있고 폰트 선택에 품질이 크게 좌우된다.
- **비용**: 중간~높음. 레이아웃 재설계가 핵심이라 CSS 재작성 범위가 넓다.

### F. 회로 기판 (PCB)

- **축**: 기판 녹색 · 금색 패드, 트레이스 선으로 섹션 연결.
- **강점**: 하드웨어 정체성이 강하다.
- **약점**: 소프트웨어 프로젝트(봇 · LLM 도구 · 웹)와 어긋난다. 실제 포트폴리오
  구성은 소프트웨어가 더 많다.
- **비용**: 높음.

### 결정 — **A. 우주 · 별자리로 확정** (2026-08-17)

저장소 소유자 결정. 청사진·터미널 계열은 반려됐다. A는 위 표에서 콘텐츠 적합·비용이
최상위가 아니지만 소유자가 컨셉의 정체성을 우선했다. 따라서 아래 조건들이
가독성·성능 리스크를 상쇄하는 전제가 된다.

#### 실패·진행 상태 은유 — 별의 생애주기

컨셉 A의 최대 난제로 지적했던 "부정 정보를 별 은유로 어떻게 쓸 것인가"는
별의 생애주기를 쓰면 억지 없이 맞아떨어진다.

| 사이트 상태 | 천체 | 근거 |
|---|---|---|
| 완료 프로젝트 | 주계열성 | 안정적으로 빛나는 단계 |
| 진행 중 | 원시성(protostar) | 아직 점화 전 |
| **실패** | **갈색왜성** | **질량이 부족해 핵융합에 이르지 못한 천체** |
| 수상 4개 | 밝기 등급(1~4등성) | `award-rank 01~04`가 실제 의미를 얻는다 |
| 카테고리 | 별자리 선 | 분야로 별을 잇는다 |
| 연도 그룹 | 관측 시기 | |

갈색왜성은 "시도했으나 점화하지 못한" 실제 천체라 자기비하 없이 실패를 표현한다.
`01~04`는 지금 단순 순번이라 #112가 "랭킹처럼 보이지만 의미가 없다"고 지적했는데,
**밝기 등급으로 재해석하면 제거 대신 의미 부여가 가능해진다.**

#### 구현 시 반드시 지킬 것

1. **배경은 정적 SVG + CSS만.** 캔버스 상시 rAF는 금지 — v2.1.0에서 없앤 문제(#113 P1-1)를
   되살리게 된다. `hero-grid-bg`·`hero-glow` 레이어 슬롯이 이미 있어 DOM 추가가 거의 없다.
2. **라이트 모드는 성도(星圖) 반전.** 흰 종이에 검은 별. 우주 컨셉의 라이트 모드는 대개
   실패하므로 "다크 = 밤하늘 / 라이트 = 인쇄된 성도"로 역할을 나눈다.
3. **기본/대체 관계 반전.** 현재 `:root`가 라이트(`#faf7ee`)이고 `[data-theme="dark"]`가
   오버라이드 18개다. 우주는 다크가 기본이라 이 구조를 뒤집어야 하며 18개가 재작성 대상이다.
4. **muted 계열 대비 재측정.** impeccable `gray-on-color` 안티패턴이 여기서 터진다.
   v2.1.0에서 만든 `--*-text` 토큰 방식(장식색과 텍스트색 분리)을 그대로 이어간다.

#### 현재 코드의 출발점 (실측)

우주 컨셉은 생각보다 유리하다 — **다크 팔레트가 이미 남색 계열이다.**

```css
[data-theme="dark"] { --paper: #1a1a2e; --paper-2: #16213e; --card: #1f2937; }
```

반대로 걸림돌은 `rgba(31, 28, 20, …)` 라이트 잉크색 **25곳 하드코딩**이다.
다크에서 따라오지 않으므로 Phase 1 토큰화가 선택이 아니라 전제다.

## 4. 참고 저장소에서 가져올 규칙

이슈 #114 댓글의 세 저장소에서 이 프로젝트에 바로 적용할 수 있는 항목만 옮긴다.

### `3x-haust/oh-my-design` — 결정 순서

컨셉을 먼저 그리지 않고 아래 순서를 지킨다.

```text
brief → evidence → copy → typography → composition → build once → critique
```

핵심은 **"레이아웃 전에 문구를 먼저 확정한다"**는 것이다. v2.1.0에서 문구를
정리한 것이 곧 이 단계에 해당하므로, v3은 composition부터 시작할 수 있다.

### `pbakaus/impeccable` — 피해야 할 패턴

- 과다 사용 폰트(Inter 등) 사용 금지
- 컬러 배경 위 회색 텍스트 금지 → **우주 컨셉(A)에서 특히 위험**
- 순수 검정 · 순수 회색 대신 톤을 넣을 것
- 카드 중첩 과다 금지 → 현재 `.about-card > .mbti-card` 구조가 이미 해당
- bounce · elastic 이징 금지 → **v2.1.0에서 해소** (`--ease-out` 토큰으로 교체)

> 이 규칙들은 README 요약이 아니라 저장소의 detector 규칙(`scripts/detector/`, 59개)을
> 실제로 실행해 확인했다. v2.1.0 적용 후 149건 → 31건이며, 남은 31건은 노트 컨셉
> 자체(견출지 탭 · 종이 배경 · 노트 줄)라 v3 교체에서 사라진다.

### `emilkowalski/skills` — 모션

- 진입 애니메이션은 `ease-out` — `STANDARDS.md` 권장 커브
  `cubic-bezier(0.23, 1, 0.32, 1)`를 `--ease-out` 토큰으로 도입 완료
- 단색 테두리보다 반투명 그림자
- UI 애니메이션은 300ms 이하, `transform`·`opacity`만 애니메이트
- 빈도표: 하루 수십 회 발생하는 hover 모션은 "제거 또는 대폭 축소" 대상
- **모든 요소가 움직일 필요는 없다** → PR #112가 센 부수 인터랙션 9종과 직결
