- 대상: PR #112의 `portfolio-information-analysis.md`, `project-audit.md`
- 기준: `main` @ `e2acc56`
- 제품 코드 변경: 없음

## 결론

PR #112의 핵심 문제 제기는 실제 저장소와 대체로 일치한다. 다만 문서의 S/A/B/C 등급은 객관적 점수가 아니라 **메인 노출 우선순위를 위한 편집 제안**이며, 집계 숫자는 `projects.json` 카드 31개만의 단순 합계로 읽으면 안 된다.

## 확인된 항목

- 동일한 1인 개발 역할 문구가 6개 상세 페이지에 반복된다.
- `그 외 다수` 표현이 여러 상세 페이지에서 반복된다.
- `projects/Sibal_Life_Smoking/_archive.html`에는 `noindex`가 없고 현재 `robots.txt`에도 해당 경로를 막는 규칙이 없다.
- Swordmaster 메인 카드의 GitHub 링크는 프로젝트 저장소가 아니라 사용자 프로필을 가리킨다.
- `Koreatech_map`의 진행/실패 중복 노출처럼 문서가 지적한 구체적 정리 후보에 저장소 근거가 있다.

## 집계 숫자 해석

`project-audit.md`의 다음 표기:

```text
S 3 / A 8 / B 10 / C 6 + 실패 5
```

는 31개 프로젝트 카드만을 서로 배타적으로 분류한 숫자가 아니다. 감사 범위에는 카드 목록 밖의 숨김/보관 상세 페이지(`Sibal_Life_Smoking`)도 포함되어 있다. 따라서 단순 합산하면 32처럼 보이는 것은 **평가 범위가 카드 목록보다 넓기 때문**이다.

이 숫자는 다음처럼 읽는다.

- S/A/B/C: 메인 노출과 보강 우선순위를 정하기 위한 편집 등급
- 실패 5종: `projects.json`의 실패 그룹을 별도 묶음으로 다룬 표기
- 숨김/보관 상세 페이지: 카드 수와 별개로 감사 대상에 포함될 수 있음

향후 문서를 다시 작성한다면 "카드 31개 분류"와 "상세 페이지/숨김 자산 감사"를 별도 표로 분리하는 편이 명확하다.

## 주관적 제안과 사실의 구분

다음은 저장소에서 사실 여부를 확인할 수 있는 항목이다.

- 링크가 잘못 연결되어 있는지
- 같은 문구가 반복되는지
- 사진/영상/상세 페이지가 존재하는지
- 같은 저장소가 여러 카드에서 참조되는지

반면 다음은 편집 판단이다.

- 대표 프로젝트를 5개에서 3개로 줄일지
- 어떤 프로젝트를 S/A/B/C로 둘지
- MBTI 등 특정 섹션을 줄이거나 제거할지
- 프로젝트를 연도순 대신 강도순으로 재배치할지

따라서 이 감사 문서를 근거로 실제 프로젝트를 삭제하거나 강등하는 작업은 자동으로 수행하지 않는다.

## 검증 범위 제한

이 PR은 문서만 추가하며 사이트 런타임을 바꾸지 않는다. 현재 연결 환경에서는 로컬 Node/브라우저 실행이 불가능해 다음은 실행하지 않았다.

```text
node -c build.js
node -c script.js
node build.js
node tools/verify-build.js
```

실제 브라우저에서 "대표 프로젝트까지 몇 스크롤인지" 같은 시각적 수치는 정적 계산 기반 근사치로 읽어야 한다.
